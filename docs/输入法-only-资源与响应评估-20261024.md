# 仅输入法模式：资源占用与响应速度评估（2026-10-24）

> 目的：语音输入全关、只用倾听输入法打字时，整个套件占多少资源、按键响应多快、还能不能优化。
> 结论先行：**Rime 计算层已经很快（p50 ≈ 0.25ms/键），真正的浪费在 `listen.exe` 常驻（语音预热 5% 单核）和 400MB 语法模型的映射；IME 本体 72MB 属于中等，比微软拼音重、比搜狗/微信轻。**
> 证据级别：资源数字是 E2（本机实测）；响应是 E2（独立 Rime API 压测，非 UI）；排名是 E1/外部资料，非权威。

---

## 0. 测试环境与一个前提

| 项 | 值 |
|---|---|
| CPU / RAM | i5-14600KF（14C/20T）/ 32GB |
| 输入法 | Weasel 0.17.4 + rime-ice（雾凇）+ 万象语法模型 400MB |
| 语音端 | listen v0.1.3，`--managed` 常驻 |
| **语音开关** | **`voice_enabled = true`（实际没关！）**，麦克风已打开（RMS≈0.0008），F9 钩子已装 |
| 采样时间 | 2026-10-24 01:20–01:45（+08:00） |

> ⚠️ 你说的“语音输入全链路关闭”与现场不符：`K:\app\AIVoice\config.toml` 里 `voice_enabled = true`，
> `listen --status` 也报 `voice_enabled: true`、`mic.opened: true`、`hook.installed: true`。
> 所以下面的 54MB / 5% CPU 是“语音开着但模型已释放”的数字；真正关掉后会更低（见 §3.2）。

## 1. 资源占用（E2，本机实测）

### 1.1 进程常驻

| 进程 | Working Set | Private | Peak WS | CPU（本次累计） | 说明 |
|---|---:|---:|---:|---:|---|
| `WeaselServer.exe` | **72.2 MB** | 77.3 MB | 82.2 MB | 10.2 s | 输入法本体（rime.dll 3.5MB + 词库/语法 mmap） |
| `listen.exe` | **54–55 MB** | 204.7 MB | **5286.9 MB** | 82.6 s | 语音端常驻；峰值是之前加载 ASR 留下的 |
| `ChsIME.exe`（微软拼音） | 35.9 MB + 18.3 MB（两个进程） | 12.0 + 5.2 MB | 37.2 MB | 0.7 s | 对照组 |
| `TextInputHost.exe` | 60.0 MB | 61.5 MB | — | 16.0 s | Windows 输入体验（共享，不算纯 IME） |

- **WeaselServer 72MB** = Rime 引擎 + 已加载的 `rime_ice` 词库/语法映射。`rime.dll` 只有 3.5MB；大头是 mmap 的词表（`rime_ice.table.bin` 60.6MB）和 400MB 语法文件里被触碰的页。
- **listen 55MB WS / 205MB Private**：WS 不高，Private 大是历史峰值（5.3GB 的 ASR）之后分配器没还给系统；**重启 listen 会明显降低 Private**。
- **微软拼音本机 36MB（+18MB）**；网上常说的“10–20MB”偏乐观，但量级一致。
- 若只看 IME，**Weasel 72MB ≈ 微软拼音的 1.5–2 倍**；把 listen 也算进“整个程序”，合计 **≈126MB**。

### 1.2 空闲 CPU（5 秒采样）

| 进程 | 5s CPU 增量 | 占单核 | 占整机（20T） |
|---|---:|---:|---:|
| `listen.exe` | 0.25 s | **~5%** | ~0.25% |
| `WeaselServer.exe` | 0.00 s | ~0% | ~0% |

`listen` 的 5% 单核主要来自**麦克风预热采集 + 重采样**（`prewarm_capture=true`，`prewarm_idle_minutes=0` 永不关麦），不是 Rime，也不是 20ms worker 轮询。
线程 CPU 也印证：一个线程 66.6s、一个 13.5s、一个 6.8s（音频回调/worker/GUI 量级），Weasel 基本为 0。

### 1.3 Rime 磁盘/映射资产

| 文件 | 大小 | 说明 |
|---|---:|---|
| `build\rime_ice.table.bin` | 60.6 MB | 主词表（含 tencent 大词库） |
| `build\rime_ice.prism.bin` | 40 KB | 拼音棱镜 |
| `wanxiang-lts-zh-hans.gram` | **400.3 MB** | 万象语法模型（mmap，按需换页） |
| 用户目录合计 | ~663 MB（含 userdb/grammar） | 不含模型 |

## 2. 按键响应（E2，独立 Rime API 压测）

### 2.1 方法

- 把 `%APPDATA%\Rime` 复制到 `K:\temp\rimebench`（不含 userdb），用 **已安装的 rime.dll** 起独立进程；
- `RimeSetup → RimeInitialize → RimeStartMaintenance → RimeSelectSchema("rime_ice")`；
- 每个样本重复 30 次：逐键 `RimeProcessKey`，最后 `RimeGetContext`；统计 p50/p95/max；
- **不经过 Weasel UI/IPC，也不合成任何键到你的桌面**。
- 压测用的是 2026-10-24 01:21 部署的 schema（当时还是每页 5/25）；之后改成 7/35 只影响候选数量与 Lua processor，单键开销同量级。

### 2.2 结果（含语法模型）

| 输入 | 键 p50 | 键 p95 | 键 max | GetContext p50 | GetContext p95 |
|---|---:|---:|---:|---:|---:|
| `shang` | 0.244 ms | 0.510 ms | 1.09 ms | 0.187 ms | 0.241 ms |
| `nihaoshijie` | 0.253 ms | 0.408 ms | 0.78 ms | 0.270 ms | 0.522 ms |
| `jieshengwei` | 0.265 ms | **1.715 ms** | 2.50 ms | 0.531 ms | 0.776 ms |
| `woxiangmaigerx` | 0.250 ms | **1.454 ms** | 2.12 ms | 0.561 ms | 0.705 ms |

- **纯 Rime 计算层：p50 ~0.25ms/键，p95 0.4–1.7ms**。`jieshengwei` 的尖峰来自热词/用户词/置顶短语，不是 Lua 或语法。
- **schema 首次加载 91ms**（`RimeSelectSchema`），这是切窗口/重启后第一键可能“顿一下”的量级。
- 这个数字**不包含** Weasel 的 IPC、DirectWrite 排版、窗口绘制；体感延迟通常还要加 3–15ms。

### 2.3 关掉语法模型 / Lua 过滤器的 A/B

| 配置 | 键 p50（4 组） | 键 p95 | 内存（进程 RSS 增量） | 结论 |
|---|---|---:|---:|---|
| 语法开（现状） | 0.24–0.27 ms | 0.4–1.7 ms | 基准 | — |
| 语法关（`.gram` 改名） | 0.25–0.28 ms | 0.3–1.6 ms | **−6 MB**（短测） | 速度没变，只省一点常驻页 |
| Lua/emoji/简繁过滤器全关 | 0.25–0.27 ms | 0.45–1.7 ms | +0.4 MB | 速度没变 |

> 结论：**当前这套词库/语法配置下，Rime 计算层没有可测的“慢”**。关语法/关 Lua 不会让打字更快，只会掉功能；它们主要是**内存/稳定性**选项，不是速度选项。

## 3. 优化空间（按性价比排序）

### 3.1 最大的一项：只用输入法时，退出 `listen.exe`

- **收益**：−55MB WS、−5% 单核（语音开着时）；若已关语音，约 −50MB、−<1% 单核。
- **代价**：托盘图标/设置页/F9/悬浮窗/快捷输入展开（`quick_expand`）都没了；热词学习日志不再增量导入（下次启动会补）。
- **输入法本身完全不受影响**：WeaselServer 是独立进程，`listen_hotwords.txt` 已经在用户目录。
- 这是“整个程序”口径下最划算的优化，**不需要改代码**。

### 3.2 保留 listen，但真正关掉语音

- 设置页/托盘把「语音引擎」关掉（或 `voice_enabled=false` 后重启）。
- 代码路径（`main.rs::voice_off`）：`drop_capture` → `asr=None` → 卸 F9 钩子 → `ST_DISABLED`。
- **预期**：麦克风采集那 ~5% 单核消失；WS 约 50MB；Private 需要重启才降。
- 当前 `voice_off.flag` 不存在、`voice_enabled=true`，说明**还没真正关**。

### 3.3 语音仍要用：把预热关掉/缩短

- `prewarm_capture=false`：省 ~5% 单核，代价是每次按下丢 0.1–0.35s 起头（项目文档已量化）。
- `prewarm_idle_minutes` 从 0 改成 5/10：不用时自动关麦，省电但下一次按下要等预热。

### 3.4 Rime 内存：语法模型与词库

| 手段 | 省多少 | 速度 | 代价 |
|---|---:|---|---|
| 关语法（`grammar=false` / 移走 `.gram`） | 400MB 映射；短测只 −6MB 常驻 | 无变化 | 长句/候选排序变差 |
| 去掉 `cn_dicts/tencent` 大词库 | 表 60.6MB 可降一截（未实测） | 加载/查找略快 | 词量变少 |
| 关 emoji/简繁 OpenCC | 很小 | 很小 | 丢表情/简繁 |

> 语法模型是 **mmap 的 400MB 文件**，不等于 400MB 常驻；32GB 机器上不建议为省内存关它。只有内存吃紧/机械盘冷启动才考虑。

### 3.5 Lua 过滤器

- 现状 filters：`corrector / autocap / v_filter / pin_cand_filter / long_word_filter / reduce_english_filter / emoji / traditionalize / search@radical_pinyin / uniquifier`。
- 我们的 A/B：**全关也没有可测的按键收益**（p50 不变）。
- 但上游 Weasel 维护者明确说过「別用 Lua」，issue #1478 里大量“Lua 导致卡顿/崩溃”的报告；**如果你遇到长句卡顿/崩溃，第一个砍 `search@radical_pinyin`（部件反查），其次 `long_word_filter`、`reduce_english_filter`**。
- 不建议为了“快”盲砍；当前数据不支持。

### 3.6 listen 的 20ms 轮询

- Worker 20ms `recv_timeout` → 50 次/秒；voice off 时没有实时性需求，可放宽到 100ms，省一点唤醒。
- 这是**代码改动**，收益 <0.2% 单核；优先级低。

### 3.7 UI 层

- 候选 35 个/5 行的排版、DirectWrite 字体回退（`weasel.yaml` 的 emoji 字体链很长）可能有几 ms 成本，但没有合成按键就无法量化。
- 真正要提速，先做 **A/B 体感**：同一段文字，在 Weasel / 微软拼音 / 搜狗 下各打 20 次，记录“首键出候选”的主观延迟；这是唯一靠谱的排名方法。

## 4. 在 Windows 输入法里的“排名”

> **没有权威排名。** 厂商不会公开同口径数据；网上只有零散实测/软文，而且“内存”常把共享页、缓存、多进程算混。下面只给可核对的口径。

### 4.1 内存（本机实测 + 公开 anecdote）

| 输入法 | 口径 | 数字 | 来源 |
|---|---|---:|---|
| 微软拼音 | 本机 `ChsIME` 两进程 | 36 + 18 MB | E2 本机 |
| 基础 Rime（小狼毫+普通词库） | 作者实测 | 20–30 MB | [aiec.fun](https://www.aiec.fun/%e5%bc%83%e7%94%a8%e6%90%9c%e7%8b%97%ef%bc%8c%e6%8b%a5%e6%8a%b1%e4%bc%98%e5%8c%96%e7%89%88rime%ef%bc%9a%e6%88%91%e7%9a%84%e8%be%93%e5%85%a5%e6%b3%95%e6%8d%a2%e8%a1%80%e4%b9%8b%e6%97%85/) |
| **本套件 IME** | 本机 `WeaselServer` | **72 MB** | E2 本机 |
| 搜狗 | 7–8 个进程合计 | ~200 MB | 同上 |
| 微信输入法 | 专用内存 | 192 MB（另有 524MB/1GB 报告） | [V2EX](https://global.v2ex.co/t/1203815) |

- 只算 IME：**微软拼音 < 本套件 ≈ 基础 Rime 的 2–3 倍 < 搜狗/微信**。
- 算“整个程序”（含 listen）：**126MB**，落在 Weasel 与搜狗之间；退出 listen 后回到 72MB。

### 4.2 响应速度

- 没有公开、可复现的“输入法延迟排行榜”。[SogouGuide 的对比](https://sogouguide.com/comparison/sogou-vs-microsoft-pinyin/) 引用了一个知乎主观排名：**微软≈谷歌≈百度（流畅）> 手心≈QQ > 搜狗（卡顿最明显）**；这是软文/主观，只能当参考。
- 本机 Rime 计算层 **p50 0.25ms/键**，这个量级不会成为瓶颈；体感差异主要来自 UI/IPC/字体和词库冷启动。
- 上游 [Weasel issue #1478](https://github.com/rime/weasel/issues/1478)：Lua 插件确实造成过 2–10s 卡顿/崩溃；**这是 Rime 系最大的速度风险，不是本套件特有**。

### 4.3 一句话排名（本机口径，仅供参考）

- **内存**：微软拼音（~36MB）< 本套件 IME（72MB）< 搜狗（~200MB）≈ 微信（~192MB+）。
- **响应**：Rime 计算层与微软拼音同一档（都是本地、无云）；搜狗/微信因云候选/AI 功能，首候选有时更慢，但没有可信横评。
- **稳定性**：微软拼音最稳；Rime 系取决于 Lua/词库，当前配置没有明显问题。

## 5. 建议执行顺序

1. **先确认真关语音**：设置页关「语音引擎」，重启 listen；再采样一次（预期 CPU 从 5% 降到 <0.5%，WS ~50MB）。
2. **如果只用输入法**：直接退出 `listen.exe`（托盘退出）。这是最大、零风险的优化。
3. **保留语音**：把 `prewarm_capture` 改成 false（或 `prewarm_idle_minutes=5`），按需开麦。
4. **Rime**：不要为速度关语法/关 Lua（实测无收益）；只有内存吃紧才考虑去 `tencent` 词库或关语法。
5. **遇到卡顿**：按 `search@radical_pinyin` → `long_word_filter` → `reduce_english_filter` 的顺序做 A/B，不要一次全关。
6. **要排名**：用同一段文字在 Weasel/微软拼音/搜狗各打 20 次，记录首键出候选的体感；网上排名不可复现。
