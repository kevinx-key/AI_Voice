# 中文拼音能力：微信输入法 vs 我们 — 技术评估报告

> 日期：2026-10-05 ｜ 对象：倾听输入法（Rime 栈）中文拼音输入质量
> 结论一句话：**微信的护城河是「云端神经语言模型 + 亿级用户行为数据」，这两点在我们"本地优先 + 隐私红线"的定位下无法照搬；但"语义级排序 / 联想 / 词库"三块可以显著逼近，尤其"本地 LLM 候选重排"是最强杠杆。**

---

## 0. TL;DR（先看这个）

- 我们与微信**不是同一个架构量级**：我们是 librime 1.13.1 的"静态词库 + n-gram 组句"，微信是"云端 Transformer LM + 海量个性化数据"。
- 差距**可缩小**的三块：① 语义级候选排序（本地 LLM 重排）② 词库规模/新鲜度 ③ 联想与纠错。
- **不可追平**的两块：云端亿级数据、跨源个性化画像（架构/隐私决定）。
- 我们手里有三张牌被低估：**万象 400MB n-gram**（已装、参数未调优）、**本地 Qwen3.5-4B / llama-server**（现在只用于润色、可复用做重排）、**已编译但未启用的 `predict` 插件**（可做基础联想）。
- 见效最快的三步（1–3 天、低风险）：打开 `translator/contextual_suggestions`、扩词库、开模糊音。
- 最能追平微信的一步（1–2 月、中风险）：**本地 LLM 重排候选**（已有开源验证：llm-ime / lime 思路，350MB 量化模型即可跑）。

## 1. 双方架构对比

### 1.1 微信输入法（公开信息 + 行业通识推断）
- **多层引擎**：拼音纠错层 → 组句层（语言模型）→ 候选排序层 → 个性化重排层。
- **语言模型**：**云端深度神经网络 LM（长上下文）**，语义级打分；新词/热词云端实时更新。
- **词库**：亿级互联网语料 + 人名/地名/专业/网络流行语，日更。
- **个性化**：本地学习 + 云端画像（用户词、常用句、联系人、场景、跨设备同步）。
- **容错**：模糊音、拼写纠错、错别字纠正、中英混输、长句联想。
- **场景**：能感知聊天/搜索等场景（隐私上界有争议，曾因"上传输入内容"被讨论，后改为本地/可选）。

### 1.2 我们（Rime 栈，实测）
| 组件 | 现状 |
|---|---|
| 引擎 | librime **1.13.1** + 插件 `lua` / `octagram`(n-gram 语法) / `predict`(联想，**未启用**) |
| 方案 | 雾凇拼音 `rime_ice`（整句用 `script_translator`），挂 `melt_eng`(英文)/`cn_en`(混输)/`radical_pinyin`(拆字)/`custom_phrase` |
| 语言模型 | **万象 LTS n-gram**（`wanxiang-lts-zh-hans.gram` 400MB，octagram 8 阶）+ collocation 权重 |
| 词库 | `base`(15.8MB)+`ext`(11.4MB)+`tencent`(16.5MB)+其它 ≈ **43MB**，静态、无更新 |
| 排序 | 词典词频 + n-gram collocation + 若干 lua filter（长词优先/置顶/降英） |
| 关键开关 | `translator/contextual_suggestions = **false**`；无 `predictor`；模糊音默认关 |
| 个性化 | 仅 Rime userdb（你自己打过的），无跨源 |
| 额外资产 | **本机 llama-server + Qwen3.5-4B**（现仅用于"文本整理/润色"） |

### 1.3 差异的本质
- Rime 的 `script_translator` = **词图 + beam search**，打分靠"词频 + n-gram"。**n-gram 上下文短（8 阶≈8 个词），无真·语义理解**。
- 微信 = **神经 LM 对整个上下文（含跨句）做概率建模**，天然理解话题/风格/句法。
- 一句话：**词频统计 vs 语境理解**。这就是你感觉"没那么聪明"的根因，不是调参能补的。

## 2. 逐维度差距

| 维度 | 微信 | 我们现状 | 差距 | 可缩小程度 |
|---|---|---|---|---|
| **整句/长句** | 神经 LM 语义排序 | 词图 + 万象 8-gram | 大 | 🔶 中（靠 LLM 重排/更强 LM） |
| **候选排序** | 语境重排 | 词频 + collocation | 大 | 🔷 高（LLM 重排） |
| **联想/下一词** | 强（句内+跨句+场景） | **功能没开** | 中 | 🔷 高（开 `contextual_suggestions` / `predictor`） |
| **词库规模/新鲜度** | 亿级、日更 | 43MB、静态 | 大 | 🔶 中（合并细胞词库 + 更新脚本） |
| **个性化** | 跨源画像 + 同步 | 仅本地 userdb | 大 | 🔶 中（隐私红线内可做"本地学习+导入") |
| **纠错/模糊音** | 全 | corrector 有；模糊音**默认关** | 小 | 🔷 高（配置即可） |
| **中英混输** | 流畅 | melt_eng+cn_en 可用 | 小 | 🔷 中 |
| **场景感知** | 有 | 无 | 中 | 🔷 中（TSF 可拿前台进程） |
| **多模态** | 语音/手写/翻译/剪贴板 | 语音(我们强项)+表情/计算器/日期 | 中 | 🔷 中 |
| **UI/候选交互** | 精细 | 基础（Weasel 候选窗） | 中 | 🔷 中 |

## 3. 我们现状的"真·清单"（可直接改的点）

已开（rime_ice 自带）：`enable_word_completion`、`corrector`(错音错字提示)、`emoji`、`传统化`、`date/lunar/calc/uuid/unicode`、`以词定字`、`长词优先`、`置顶候选`、`英文自动大写`、`部件拆字反查`、`中英混输`。

**关闭/缺失（本报告要动的地方）**：
1. `translator/contextual_suggestions: false`（我们自定义里写死 false）→ **联想/上下文建议没开**。
2. 无 `predictor`（`predict` 插件已编译但 schema 未用）。
3. 模糊音默认关（rime-ice 有 patch 可开）。
4. `max_sentences` 未设（且当前 librime 1.13.1 **不支持**，需 ≥1.17）。
5. 词库 43MB、无网络新词、无自动更新。
6. 无任何"语义/神经"排序。

**librime 版本是硬天花板**：我们锁 1.13.1；`max_sentences`(≥1.17)、`dictionary_exclude`(≥1.14) 等新特性用不了。**升级 librime 本身就是一条 ROI 很高的支线**。

## 4. 改进方案（A/B/C 三层）

### A 层：配置 / 词库层（1–3 天，低风险，立刻见效）
| 项 | 做法（具体） | 预期 | 风险 |
|---|---|---|---|
| 开联想 | `rime_ice.custom.yaml`：`translator/contextual_suggestions: true`（配 `contextual_suggestions_max_length`） | 出现"下一词/上下文建议"，最接近微信联想的一步 | 低 |
| 开基础预测 | schema `engine` 加 `predictor`（用已编译的 `predict` 插件）+ 配置 `predictor:` | 词级联想 | 低 |
| 开模糊音 | `rime_ice.custom.yaml` 加 `speller/algebra` derive 规则（zh/z, ch/c, sh/s, n/l, an/ang…）或指定 rime-ice 模糊音 patch | 打字容错显著提升 | 低（个别重码略增） |
| 调 corrector | `spelling_hints`、喂自定义错词表 | 错音错字提示更准 | 低 |
| 词库扩容 | 合并搜狗/百度/腾讯细胞词库 + 网络新词（见 §6） | 覆盖率↑，长尾词上线 | 中（体积/编译时间） |
| 自定义短语 | 灌 `custom_phrase.txt`（口头禅/术语/常用句） | 主观"顺手" | 低 |

### B 层：工程层（1–3 周，中风险）
- **词库工具链**：细胞词库抓取→转 Rime `.dict.yaml`→去重/赋权→定期更新脚本（可长在设置页"更新词库"）。
- **个性化**：一键导入自定义词/热词；本地 userdb 权重自适应；把用户"选过的词"回流到本地词典（不碰微信原始数据）。
- **场景化权重**：TSF 拿前台进程名 → 微信/IDE/浏览器 用不同词库权重 profile。
- **联想 UI**：把 `contextual_suggestions` / predictor 的候选在候选窗分组展示。
- **升级 librime**（1.11→1.17+）解锁 `dictionary_exclude`/`max_sentences` 等。

### C 层：架构层（1–2 月，追平关键，中高风险）
1. **本地 LLM 候选重排**（最强杠杆，见 §5）——把"词频排序"换成"语境排序"。
2. **更强 (神经) 语言模型**：量化 Transformer LM（ONNX/llama.cpp）替换/叠加 n-gram 做 beam 重排。
3. **云端 LR 重排（可选）**：硬 case 上云；受隐私红线约束，需单独授权且**只传拼音串、不传上下文**。

## 5. LLM 候选重排（C 层核心，已有开源验证）

> 参考：博主"曦远Code"的实验项目 **llm-ime**（本地 GGUF 模型接收拼音、按语境排序候选，350MB 量化即可跑），思路与"lime"一脉相承。说明这条路**已被验证可行且吃得起**。

**做法**
1. Rime 出 top-N 候选（`script_translator` + 万象 gram 的结果，含拼音 comment）。
2. 把「当前拼音串 + 上文（前 1~2 句）+ 候选列表」交给**本地 LLM**，让它按语境打分/选出最佳（或直接生成下一词）。
3. 用重排后的顺序替换候选窗（或仅把最佳项置顶）。
4. 触发时机：**按整句/停顿/上屏时**触发，**绝不逐键**（否则延迟爆炸）。

**工程要点 / 风险**
| 点 | 说明 |
|---|---|
| 延迟预算 | 目标 <150ms 才不打断输入；用 **0.5B~1.5B 量化模型**（或 Qwen 小模型）常驻，别用 4B 逐次跑 |
| 复用现有资产 | 本机已有 llama-server(Qwen3.5-4B) —— 可先做"离线批测/评估"，再上小模型做实时的 |
| 交互设计 | 重排结果**异步**回填候选窗（Rime 候选窗刷新/或我们的 Weasel 面板）——需要前端配合 |
| 抖动 | LLM 不稳定 → 只在"高置信"时重排，低置信回退 n-gram |
| 隐私 | **全本地**，天然满足红线（微信原始数据不出云端） |
| 验收 | 用固定测试集（常用句/长句/领域句）对比"重排前 vs 重排后"首选命中率 |

**预期**：常用/领域长句首选命中率可**显著提升**，是本地化达到"微信语义排序"的唯一现实路径。

## 6. 词库扩容方案

- **数据源**：搜狗/百度/腾讯**细胞词库**（各领域）、网络新词/流行语、专业词（你的键盘/嵌入式领域）、人名地名。
- **流程**：抓取 → 转 `*.dict.yaml`（`词 \t 拼音 \t 词频`）→ 与现有 `base/ext/tencent` 合并去重 → 赋权（高频/领域词高权重）→ `librime` 编译 → 增量更新。
- **更新机制**：脚本 + 版本号，设置页加"更新词库"按钮；发布走我们的安装包（离线优先）。
- **规模目标**：43MB → **100–200MB**，覆盖率接近主流商用词库。

---

## 7. 个性化方案（守隐私红线）

- **已有**：Rime userdb（本地学习你选过的词）。
- **可加**：① 自定义词/热词一键导入；② 从**我们自己的**使用记录回流（本地）；③ 可选"通讯录/术语表导入"（本地解析）。
- **不做**：读取微信聊天原始数据上云（`CLAUDE.md` 明确禁止）——这恰好是微信强而我们守线的地方；差异用"领域词库 + 本地学习"补偿。

## 8. 路线图与里程碑

| 阶段 | 内容 | 产出 | 验收指标 |
|---|---|---|---|
| P0（1–3 天） | A 层：开联想/模糊音/corrector + 词库扩容 v1 | 新安装包 | 联想出现、容错提升；主观"顺手度"↑ |
| P1（1–3 周） | B 层：词库工具链 + 个性化 + 场景化 + 升 librime | 词库更新器、profile 切换 | 新词覆盖率↑；长句首选率↑ |
| P2（1–2 月） | C 层：本地 LLM 重排 MVP（小模型常驻，按句触发） | 重排服务 + 候选窗回填 | 固定集首选命中率 **+X%**（先测基线） |
| P3 | 神经 LM 整句 / 云端 LR（可选，需授权） | 升级 LM | 长句质量接近商用 |

> 每阶段先做**基线测量**（固定测试集的首选命中率/长句正确率），否则无法判断"是否更接近微信"。

## 9. 预期收益与不可追平项

- **可达**：常用输入 80–90% 体验；领域词/长句因本地 LLM 更懂"你"甚至反超。
- **不可达**：网络新词实时性、极限联想、跨源个性化画像、跨设备同步（云端/数据壁垒）。
- **差异化**：我们是"**语音 + 键盘二合一**"，可做微信没有的融合（口述原文与拼音候选联动、语音纠错混合编辑）。

---

## 10. 风险与红线

- **隐私**：个性化必须本地；微信原始数据不得上云（硬红线）。
- **延迟**：LLM 重排必须异步 + 小模型 + 按句触发，否则毁掉输入手感。
- **维护**：词库/模型体积与更新成本；安装包会变大（现 414MB，含 400MB 语法模型）。
- **librime 升级**：动 fork 的构建链（Boost/librime/插件），有回归风险，需单独验证。

### 附：报告结论的"下一步建议"
1. 先做 **A 层 P0**（低风险、立刻有感）并**测基线**。
2. 并行验证 **C 层 LLM 重排**的最小子集（离线批测：拿本机 Qwen 重排历史输入，看首选命中率提升）。
3. 若 LLM 重排有效 → 上小模型常驻 + 候选窗异步回填。
